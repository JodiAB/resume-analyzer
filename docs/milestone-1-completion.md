# JobPilot AI — Milestone 1 completion report

27 October 2026. Status: implemented and locally verified for controlled development; stopped for review before Milestone 2. Full live security gate remains OPEN. No push, public deployment, application submission or job discovery implementation occurred.

## Delivered behavior

The new authenticated `/profile` route imports a readable master PDF, extracts every page locally with PDF.js, and proposes literal source claims for recognized CV section headings. The editor separates employment, freelance work, personal/portfolio projects, technical skills, education and certifications. Dates retain their supplied precision; missing fields and proficiency remain unknown. No experience totals, seniority inference, invented qualifications or AI calls are generated by this workflow.

Each claim includes exact page/start/end/quote evidence bound to a source text hash and original PDF byte hash. A candidate may correct values, categories and evidence; every change clears its prior confirmation. A CV-backed confirmation requires every nonempty field to appear literally in the attached passage (with a narrow case-preserving comparison for canonical `present`). Unsupported corrections require an explicit reason and remain separately labeled candidate attestations. Neither status represents independent verification by an employer or institution. Unconfirmed claims can be saved as drafts and remain visibly excluded from verified qualifications.

Preferences include job titles, locations, salary range/currency/period, hours per week, working-hour notes, own IANA time zone and desired overlap zones. Preferences are supplied by the candidate, never inferred as work authorization or qualifications. Salary order and time zones are validated.

The original PDF stays in browser memory and is not uploaded by the profile workflow. Explicit save consent sends extracted text, claims/evidence and preferences to existing private Puter KV. This is private cloud persistence used from a local controlled application, not browser-disk storage. No candidate localStorage, public CV URL, server candidate loader, second authentication provider or database migration was added. Existing analyzer functionality remains available.

## Storage and security decisions

- Key: `jp:v1:profile:<owner UUID>:<revision UUID>`. Each immutable revision has schema version, owner, parent, creation timestamp, source and preferences. Records are strictly validated on reads and writes; mismatched owner/key, invalid evidence, corrupt source hash, missing parents or cyclic history fail closed.
- Reuses actual guarded Puter KV operations plus captured-session checks at asynchronous boundaries. Guarded SDK pre/post identity checks reject out-of-band changes; PrivateBoundary unmounts private views when identity becomes ambiguous or changes.
- Web Locks are required for same-origin writes. Inside the lock, reload remote revision leaves before saving. Multiple leaves block editing. There is no mutable authoritative head pointer and no blind write retry.
- Immutable same-ID readback reconciles lost receipts. Reconciliation also verifies that the revision is still the sole current leaf. Unconfirmed save outcomes retain the draft for same-ID retry; errors do not claim success.
- Bounds: 20 MB PDF; 50 pages; 100,000 characters per page and 300,000 source characters total; 200 automatic suggestions / 250 total claims; 1,500,000 serialized characters per revision; 100 revisions and 15,000,000 aggregate serialized characters. Projected history size is checked before writing. Records are not automatically pruned or broadly deleted.
- This is defense in depth in the client. Puter service permissions remain the access-control boundary; owner fields are not a substitute for service authorization. No production-security certification is made.

## Failures found and repaired

Tests were added before the corresponding implementation increments. Initial imports failed because modules were absent; focused tests then passed after implementation. A later safe-return test first reproduced the missing `/profile` sign-in return path and passed after allowlisting it.

Initial TypeScript verification found strict narrowing errors in schema validation and an overly narrow test dependency return type. Both were corrected; final TypeScript verification passed. A component test initially omitted the blur event that commits a comma-separated preference field; it was corrected to exercise the actual UI event contract, then saved/reloaded successfully.

Fresh code review identified three defects, each reproduced with a failing regression and then repaired:

1. A new revision could exceed the aggregate history read limit after being written and make later loads fail. Save now checks projected history size before mutation; the regression confirms no new key and continued readability of the prior revision.
2. A literal capitalized `Present` end date was canonicalized but rejected by case-sensitive evidence validation. The narrow end-date comparison now supports it without creating dates.
3. One long skill line could bypass the suggestion count bound. The split loop now enforces the cap.

A separate regression found same-ID retry could report an old revision current despite concurrent branches; reconciliation now checks leaves before returning success. Reviewer inspected the fixes and reported no remaining important findings; reviewer did not run live SDK tests.

## Remaining release blockers and limitations

**Full live account isolation is NOT PASS.** The previously untested reverse A-to-B raw access and switching accounts while real SDK network requests are still pending remain release blockers. Live delayed consumer delivery tests from stabilization do not establish wire-level races. New profile KV data has not been tested with two real Puter accounts. Controlled SDK regressions cannot close these gates.

Puter KV size/quota behavior for maximum-size profile histories, actual deployment-origin boundaries, shared/symlink storage, provider retention, third-party SDK exposure, dependency audit and deployment headers remain unverified for release. No live model or job-source integration was tested or added here.

Web Locks serialize tabs on the same origin, not devices. Across devices, nontransactional KV can still create branches after a fresh read. Detected conflicts block further editing; there is no merge UI or global compare-and-swap guarantee. Concurrent aggregate-limit races across devices are not certified safe. Keep controlled development local and require a separate production concurrency review.

Extraction is conservative and section/line based. Nonstandard layouts may need manual structured entries and exact passage selection. Scanned CVs require a readable text version; OCR is not silently inferred. Source hashes prove consistency of captured data, not truth or external authenticity. Candidate attestations remain self-reported. No linked portfolio content is fetched.

There is no profile history pruning/deletion or conflict-merge UI in this increment. Existing analyzer wipe deliberately does not touch profile keys. Records remain private in Puter until explicitly managed; retention/erasure UX needs review before public use. Limits reject new writes while preserving accepted records. No automatic expiry or provider-level erasure is promised.
