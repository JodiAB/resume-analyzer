# Approval-first application management implementation plan

> Execute inline with TDD and one fresh feature review. User authorized Milestone5 only. Preserve343 baseline tests and local architecture. No real submissions, push or public deployment.

**Goal:** Review/approve an immutable employer-specific package, manually hand it off, explicitly confirm submission, and track progress privately.
**Architecture:** Reuse preparation snapshots/renderers and guarded Puter KV. Store bounded immutable package/state events in an owner-scoped append-only chain with Web Locks, optimistic per-application heads and exact-ID reconciliation. No employer submission API, mail or form automation.
**Spec:** User's Milestone5 attachment `62b45b53-0acc-4951-b259-eca3c7cb6115/Pasted text.txt`.

## Design decisions

- New `features/applications/{destination,model,repository,service}.ts`, focused review/tracker/handoff components, private `/applications` route, links from saved preparation. Existing source URL evidence remains available; application handoff is a separate approved action, never a discovery review-status mutation.
- Packages contain identity, exact preparation/profile/job/assessment snapshots, original/canonical official destination, candidate-confirmed screening drafts and deterministic CV/cover content + PDF/DOCX hashes. Binary files are rendered locally and not stored in KV. Immutable package hash covers every employer-facing field; choosing another revision/destination/answer creates a new package and clears approval. No automatic migration or master mutation.
- Lifecycle DRAFT → READY_FOR_REVIEW → APPROVED → AWAITING_SUBMISSION → SUBMITTED → FOLLOW_UP → CLOSED; support REJECTED/WITHDRAWN. Denying document approval returns to DRAFT (not an employer rejection). Opening a URL records no submission. SUBMITTED requires an explicit candidate statement and timestamp, labeled self-reported. Repeated confirmation is rejected; exact lost-receipt retries reconcile once.
- Approval requires intentional checkbox acknowledgements of employer/destination/CV/cover/answers, exact displayed hash, valid source/ownership, complete contact/edits/screening and actual regenerated file-hash equality. INELIGIBLE blocks approval; UNKNOWN needs explicit uncertainty acknowledgement/reason. Unknown is never relabeled eligible. New selected package invalidates approval even if the old version was approved. Submitted packages are immutable: future reapplication is a separate explicit attempt; notes/response/follow-up metadata never changes approved content.
- Official handoff is limited to reviewed catalog ATS hosts and exact source-board-vacancy paths. HTTPS only, no credentials/private hosts/encoded traversal/arbitrary parameters or redirect-style query strings. Canonical tracking/apply variants deduplicate. Unknown/custom destinations are blocked pending review, not guessed. Employer-server redirects cannot be certified by a client; no automatic redirect-following or candidate data is added to URLs.
- Canonical vacancy identity is durable, independent of browser state. A second application requires explicit reapplication confirmation plus a recorded reason; preserve earlier attempt/submission history. Web Locks serialize same-origin tabs, expected application head rejects stale edits, any cross-device event fork fails closed. No claim of cross-device transaction guarantees or live service isolation.
- Handoff state offers approved downloads and safe local answer copy, plus an explicit user action to open the official page with no opener/referrer and no private query/body. Source/approval checks repeat at action time. Tracking continues after submission even when historical job/profile sources expire; historical facts are not silently reset. Historical approved-file hashes must still match exact regenerated bytes; no new employer handoff from terminal/submitted records.
- Interview/offer progress is separate tracking metadata alongside lifecycle: employer response, interview stage/time, follow-up date and optional notes. Search/sort/filter runs locally. No automation/reminder is created merely for stored follow-up dates.
- Maintain release-blocker register: full live multi-account isolation, real network races, deployment origin, native DOCX appearance (LibreOffice missing), live paid-model verification and retained dependency advisories. Review audit; do not silently upgrade unrelated dependencies or close blockers.
